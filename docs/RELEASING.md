# Releasing JellyFreedom

Releases are cut by `.github/workflows/release.yml` from a `v*` tag. Nothing is built on a
laptop any more: the workflow cross-compiles both architectures, generates `SHA256SUMS`,
signs build provenance, and opens a **draft** release for you to review and publish.

## The `release/build.sh` contract

`release.yml` invokes the build script like this, once per architecture:

```bash
JF_VERSION=<version> GOOS=linux GOARCH=<amd64|arm64> CGO_ENABLED=0 \
  ./release/build.sh <version>
```

and requires the following behaviour:

| Input | Meaning |
|---|---|
| `$1` (positional) | The version. Kept for backwards compatibility. |
| `JF_VERSION` | The version. Takes precedence over `$1` if both are set. |
| *(neither set)* | Fall back to the contents of the `VERSION` file — **never** to a date. |
| `GOOS` / `GOARCH` | Passed straight through to `go build`. Default `linux` / host arch. |

| Output | Requirement |
|---|---|
| `dist/jellyfreedom-<version>-<goos>-<goarch>/` | The staged bundle directory. |
| `dist/jellyfreedom-<version>-<goos>-<goarch>.tar.gz` | Exactly **one** `*.tar.gz` per invocation under `dist/`. |
| `dist/jellyfreedom-<version>-<goos>-<goarch>.tar.gz.sha256` | Convenience digest for local builds. Not published; the release's `SHA256SUMS` is generated by the workflow. |
| `<bundle>/VERSION` | Contains the version string. |
| `<bundle>/bin/orchestrator` | Static (`CGO_ENABLED=0`), `-trimpath`, built for `$GOARCH`. |
| `<bundle>/vpntorrent/jf-netns-helper` | Required. `build.sh` hard-fails without it — a bundle missing the privileged helper installs a system whose VPN controls silently do nothing. |
| Version stamping | Built with `-ldflags "-s -w -X main.version=<version>"`. |

`build.sh` cleans only its own outputs, never `dist/` wholesale, because a maintainer's
`dist/` may hold previously published artifacts. Each CI job builds one architecture on a
clean runner, so the "exactly one tarball" rule still holds there. The workflow fails
loudly if `dist/` contains zero or more than one tarball.

Both `build.sh` and the workflow independently verify the binary's actual machine type with
`file`, so a build that silently ignores `GOARCH` fails rather than shipping an amd64 binary
under an arm64 name.

## Version stamping

The version must come from one place. `cmd/orchestrator/main.go` declares:

```go
var version = "dev"
```

built in with `-X main.version=<version>` and reported by `GET /healthz`. Do not hardcode
a version literal in Go source — the workflow's tag/`VERSION` cross-check will not catch it,
and it has drifted before.

## Release checklist

1. **Land everything** for the release on `main`, with CI green — including the
   `installer-smoke` job. A release whose installer has not been smoke-tested end to end is
   not ready.
2. **Run `release/bump.sh`.** It does steps 2, 3 and 5 of the old manual checklist together,
   because getting one of them right and another wrong is how a tag lands that the workflow
   then refuses to build:

   ```bash
   ./release/bump.sh patch     # 0.5.1 -> 0.5.2   a fix
   ./release/bump.sh minor     # 0.5.1 -> 0.6.0   a feature
   ./release/bump.sh major     # 0.5.1 -> 1.0.0   a break
   ./release/bump.sh 1.2.3     # an exact version
   ```

   It writes `VERSION`, renames `## [Unreleased]` to `## [<version>] - <today>`, opens a
   fresh `## [Unreleased]`, repoints the comparison links, commits on a `release/<version>`
   branch, and prints the remaining commands.

   It refuses to run on a dirty tree, on a version that already has a tag, or when
   `## [Unreleased]` is empty — an empty section would publish empty release notes to
   everyone watching. Before committing it re-runs **the workflow's own extraction** against
   the file it just wrote, so a layout change is caught here rather than after the tag is
   pushed.

3. **Re-read `SECURITY.md`** if routes or authentication changed in this cycle.
4. **Open the PR, let CI finish, merge it.** `main` is protected: it takes pull requests
   only, and all eight CI jobs must pass. This is deliberate — the tag in the next step is
   what publishes, so the commit it points at should be one CI has already agreed with.
5. **Tag the merged commit and push the tag:**
   ```bash
   git checkout main && git pull
   git tag -a v0.3.0 -m 'JellyFreedom 0.3.0'
   git push origin v0.3.0
   ```
   Pushing the tag is what triggers the build. `main` itself is already up to date by this
   point, because the bump went in through its pull request.
6. **Watch the workflow.** It builds `linux/amd64` and `linux/arm64`, verifies each binary's
   machine type, generates `SHA256SUMS`, attests provenance, and creates a **draft** release.
7. **Review the draft:** correct notes, and **seven** assets present — see *Asset names*
   below. The two stable `jellyfreedom-linux-<arch>.tar.gz` names are the ones the
   one-liner actually downloads; if they are missing, `get.sh` fails for every user.
8. **Smoke-test the published artifact** on a throwaway VM — never on a live box:
   ```bash
   curl -fsSLO https://github.com/MoonTheRipper/JellyFreedom/releases/download/v0.3.0/SHA256SUMS
   curl -fsSLO https://github.com/MoonTheRipper/JellyFreedom/releases/download/v0.3.0/jellyfreedom-0.3.0-linux-amd64.tar.gz
   sha256sum -c SHA256SUMS --ignore-missing
   # and the path a real user takes:
   curl -fsSL https://github.com/MoonTheRipper/JellyFreedom/releases/latest/download/get.sh | sudo bash
   gh attestation verify jellyfreedom-0.3.0-linux-amd64.tar.gz --repo MoonTheRipper/JellyFreedom
   ```
9. **Publish** the draft. Publishing is what makes
    `releases/latest/download/get.sh` resolve — the one-liner in the README points at
    `latest`, so an unpublished draft leaves users on the previous release.
10. **Verify the one-liner** resolves:
    ```bash
    curl -fsSLI https://github.com/MoonTheRipper/JellyFreedom/releases/latest/download/get.sh
    ```
11. **Update an existing install** to confirm the upgrade path:
    `sudo jellyfreedom --update` on a test box.

## Asset names

`release/get.sh` resolves its download through `releases/latest/download/<name>`, which
cannot contain a version. **The stable names below are load-bearing — do not rename them.**

| Asset | Purpose |
|---|---|
| `jellyfreedom-linux-amd64.tar.gz` | **What `get.sh` fetches on x86_64.** Stable, version-free. |
| `jellyfreedom-linux-arm64.tar.gz` | **What `get.sh` fetches on aarch64.** Stable, version-free. |
| `jellyfreedom-<version>-linux-amd64.tar.gz` | Versioned x86_64 bundle, for pinning and for the attestation subject people cite. |
| `jellyfreedom-<version>-linux-arm64.tar.gz` | Versioned aarch64 bundle. |
| `jellyfreedom.tar.gz` | **Compatibility alias** — a copy of the amd64 bundle. Required by *two* things still in the wild: the v0.2.1-era `get.sh`, **and the `jellyfreedom` control CLI shipped in v0.2.0–v0.2.1**, whose `--update` hardcodes this unsuffixed name (`git show v0.2.1:release/jellyfreedom`). Dropping it does not just break new installs — it permanently breaks `sudo jellyfreedom --update` for anyone still on ≤0.2.1, who would then need a manual reinstall to get unstuck. Keep publishing it until you are willing to strand those installs. |
| `get.sh` | The one-line bootstrap the README advertises |
| `SHA256SUMS` | Checksums for every tarball and `get.sh` |

`SHA256SUMS` must list **bare filenames with no `./` prefix**. `get.sh` matches entries with
`awk '$2 == a || $2 == "*"a'`, so a `./`-prefixed entry does not match, and `get.sh` then
refuses to install rather than installing unverified bytes. The workflow generates the file
from an explicit list and re-resolves both stable names with the same `awk` expression
before publishing, so a naming drift fails the release instead of the user.

## Re-running a release

`workflow_dispatch` accepts an existing tag, so a release can be rebuilt without re-tagging:
Actions → Release → *Run workflow* → enter `v0.3.0`. Delete the previous draft first.

## Compatibility notes

- The current `release/jellyfreedom` CLI fetches `jellyfreedom-linux-<arch>.tar.gz`, so
  once a user is on this release or later, in-place updates follow the stable arch-aware
  names and the alias is no longer on their update path.
- `get.sh` verifies the bundle against `SHA256SUMS` and **refuses to install** if the file
  is missing or has no entry for the asset (override: `JELLYFREEDOM_SKIP_VERIFY=1`). A
  release published without `SHA256SUMS`, or with `./`-prefixed entries in it, breaks the
  one-liner for everyone. The workflow checks both before publishing.

## Hotfixes

Same process with a patch bump. Do not move an existing tag — a moved tag invalidates the
provenance attestation and the published checksums.
